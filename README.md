# Sun386i in MAME

A MAME driver for the Sun386i ("Roadrunner", 1988), Sun's only x86 workstation.
It boots SunOS 4.0.1 and 4.0.2 from disk to a colour SunView desktop, with
MS-DOS 3.30 running in a window under virtual 8086 mode, sharing the file
system with SunOS in both directions.

**No dump of the machine's boot PROM is known to exist.** The driver carries a
stub instead, reconstructed by reading what the SunOS kernel asks of it: memory
size, putchar and getchar, which device is the console, the boot parameter
block, reboot, the frame buffer type, and a handful of vector slots the kernel
calls at startup that only need to return zero. Console text on the machine's
own screen is drawn by that stub with an 8x16 font, because on a real Sun that
is the PROM's job: the kernel has no glyph drawing of its own and calls the
romvec putchar at +0x18 until it takes the screen over.

No Sun software is redistributed here.

## What works

- Boots SunOS 4.0.1 and 4.0.2 from a SCSI disk, and installs from the original
  diskette set.
- Console on the machine's own 1152x900 screen, keyboard and mouse.
- The colour board (cgthree) at 0xa0400000, and SunView in colour.
- The graphical login, and a user session that comes up by itself.
- `help_viewer`, `organizer`, `coloredit`, `snap`, `mailtool`, `textedit` and
  the demonstration programs.
- **DOS windows**: MS-DOS 3.30 in virtual 8086 mode inside a SunView window,
  with the Unix file system mounted as DOS drives and Unix commands callable
  from the DOS prompt.
- Serial console on ttya, and a clean `halt`.

## Fixes to MAME's i386 core

Three of them, in `patches/i386.patch`, with the measurements that found each.
Two matter beyond this machine:

1. **A task switch reaches the GDT and both TSSes at the current privilege
   level.** Those are implicit accesses by the control unit and are always made
   as the supervisor. It goes unnoticed until something starts a task switch
   from ring 3, which is exactly how SunOS enters virtual 8086 mode: the kernel
   maps the process its own task state segment at user address 0x110000, leaves
   the nested task flag set, and the DOS emulator crosses with a plain `iretd`.
   Under MAME the switch began and never finished, because the first byte it
   touches is the busy bit in the outgoing descriptor, on a kernel only page.
   Since MAME raises faults with a C++ throw, the exception left the function
   from the middle with nothing logged.

2. **The 386 is built without a coprocessor.** `i386_device::device_start()`
   calls `build_opcode_table(OP_I386)` with no `OP_FPU`, and never calls
   `build_x87_opcode_table()` or `x87_reset()`. Every later model does all
   three. The escape opcodes are not decoded at all, so **every floating point
   result on the guest is rubbish, silently**. This affects any 386 machine in
   MAME, not just this one.

3. **IRET returns to virtual 8086 mode on the stacked VM bit alone**, without
   requiring CPL 0, so a user mode IRET could put the processor into virtual
   8086 mode by itself.

Nothing here has been sent upstream.

## Building

MAME is not included. Point `MAME_TREE` at a MAME source tree and run:

    MAME_TREE=/path/to/mame tools/build.sh

gcc 11.4 falls over with an internal compiler error at -O3 on some MAME
sources. `tools/buildone.sh <source>` rebuilds that one object at -O1 and then
the build carries on.

## A note on the PROM stub

`driver/sun386i_prom.hxx` is generated by `tools/gen_stub.py` and embeds a 2 KiB
NVRAM image from a real 386i/150, obtained from sunhelp.org. It is machine
configuration, not software, and it is there because the kernel reads it: with
the real contents it finds `artwork 3` and trusts the diskette change line,
and with a blank one it finds 255, concludes the line is broken and inverts
every reading. The driver matches the first case. Regenerating the header
without that image silently produces a machine whose floppy drive never
completes a read.
